## 4. End-to-end workflow traceability

All six scenarios below are **code traces, not executed browser scenarios**. Test evidence for individual services is listed separately. API paths are the registered backend paths; the staff client uses its configured API base.

### 4.1 Routine visit, no additional diagnostics

Shared patient search/registration (E01) → booking with specialty intent (E02) → shared OPD create/check-in (E03) → `/opd/ophthalmology?visit_id=…` (E04/E05) → `POST /api/opd/visits/:visitId/ophthalmology/context` through API/domain/service layers → `createContext` derives patient/branch/department/doctor from visit → context repository/model → returned context triggers query refresh. Intake draft/complete goes through the same visit-scoped family to E06; no emergency criteria means no alert. Baseline ordered tasks still require configured processing. Doctor uses E13 shared diagnosis save and E12 clinical review save; no additional-test creation is required merely to save assessment. E15 readiness → E16 completion → shared visit/consultation/appointment plus frozen summary/audit/timeline → invalidation/refresh. G02 sequence, G03 summary, G01 identity and G05 initial atomicity prevent certification.

### 4.2 Additional investigations

E08 create dialog → `POST /api/opd/visits/:visitId/ophthalmology/test-tasks` with idempotency key → registered route permissions/schema → E07 `createTestTask` → active catalogue and same-visit shared order/item validation → transactional task/audit persistence → task response/query invalidation → assign/call/start → E09 editor → E10 draft/complete result repository → E12 submit/review → E11 clinical review. Shared laboratory/imaging orders instead originate in E18 and persist in their existing domain; a specialty task must reference that source, not duplicate the shared verified result. Automatic source-order-to-task creation and complete same-session handoff are not established (G06).

### 4.3 Unacceptable result and repeat

E08 Repeat dialog freezes task status/version, station and reason → task repeat API (E07 registered route) with stable idempotency key → `repeatTestTask` rechecks expected state, source, eligible station and existing repeat → required transaction creates repeat and links original, updates history/audit → response becomes new task → queue refetch → new assignment/testing → separate result version → doctor review. Original completed result is not overwritten. Only COMPLETED/SUBMITTED_FOR_REVIEW sources can use this repeat action; reviewed results require the applicable amendment path. Runtime rollback/concurrency evidence remains bounded by Section 7.

### 4.4 Emergency presentation

E05 intake criterion selection and completion confirmation → intake complete API → E06 `completeIntake` validates active criteria, actor context and available authorized recipients → transaction stores completed intake, alert and notifications → response includes alert → intake/alert views refresh → clinician can acknowledge and review. A no-recipient condition returns conflict rather than pretending delivery. **Trace breaks at required bypass/priority enforcement:** E07 start logic checks station/assignee/device without requiring urgent review or recording skipped stages. Alert notification is not proof of timely review (G02).

### 4.5 Blocked completion

E15 opens summary/readiness section → readiness GET → E16 `getCompletionReadiness`/`evaluateCompletionReadiness` → repository reads configured requirements, intake, alerts, tasks/results/orders, diagnoses/review/optical/finalization → `{ready, requirements, versions}` → UI shows unmet details and resource IDs. Completion POST independently re-evaluates within transaction; unmet conditions without current matching authorized override return 409. User resolves clinical data in corresponding sections or uses reasoned deferral/override → targeted refetch → new readiness. No UI-only readiness flag authorizes completion. Safety depends on the approved profile and actual clinician identity (G01/G11).

### 4.6 Completion and downstream operations

E15 finalization dialog → complete API with frozen versions/idempotency key → E16 `completeConsultation` → required transaction updates consultation, visit, appointment, context, clinical review, completion snapshot, audit and timeline → finalization response → query invalidation and completed UI. **This method does not create invoices, submit medication drafts, book surgery, or publish portal content.** Those remain explicit E18/E19/E20 operations. Generic `completeWorkspace` has staged shared handoffs but rejects specialty completion, so its pharmacy/billing actions cannot be counted as automatic specialty integration. Explicit publication validates exact approved version, ownership/scope, fence and idempotency → publication/document metadata + timeline → patient overview parses an allowlisted payload. Verify operational pending/retry states separately; clinical success must not be presented as downstream success (G06/G14).

## 5. Defect and gap register

“Static finding” means the contradiction is visible in source; it does not claim reproduction against a clinical database. “Acceptance gap” means evidence is missing rather than code proved absent.

### G01 — Critical — Clinical approval may use a different person's doctor identity

- Requirements: 19, 32, 42b, 51, 54, 56, 57, 66.
- Evidence: E25, `ophthalmology.service.ts:1344–1353`; completion calls it at `:1082`, optical approval also calls this helper; repository stores approver user and substituted doctor at `:1047`/`:920`.
- Expected: authenticated authorized clinician has their own active doctor identity in the correct clinical scope; administrator status alone does not imply doctor identity.
- Actual: when no linked doctor is found, SUPER_ADMIN can use `visit.doctor_id`, or `getAnyActiveDoctorId(context.branch_id)` without department argument. This is an explicit clinical-identity bypass, not merely a UI permission concern.
- Impact: review/approval may be attributed to a doctor who did not perform it. The separate actor user field does not cure a misleading approver-doctor identity.
- Recommendation: require the actor's linked scoped clinical identity; any delegated/on-behalf approval needs an explicit approved contract and separate attribution. Add non-doctor admin and cross-department negative tests.
- Dependencies/modules: Ophthalmology clinical review, optical, completion, audit; clinical authorization owner. Static finding, no exploit performed.

### G02 — High — Emergency bypass and routine sequencing are not enforced

- Requirements: 11–13, 19, 26. Evidence: E06 completeIntake/routeEmergency; E07 createTestTask stage validation, start eligibility and routeTestTask; workflow stage mapping stores `bypass_allowed`.
- Expected: urgent escalation records skipped stages/reason, preserves pending work, and prevents inappropriate routine progression; sequential prerequisites are authoritative.
- Actual: alerts/notifications are real, but start eligibility only checks assignment/station/device; supplied workflow-stage membership is checked without enforcing preceding stage completion. No bypass history write was found across specialty service/repository paths.
- Impact: an emergency flag can coexist with continued routine processing; configured stage order does not guarantee care order.
- Recommendation: implement approved emergency progression/bypass and stage-prerequisite contract with stale/parallel/negative tests. Do not infer clinical urgency thresholds.
- Dependencies: workflow profiles, clinical policy, queue/notifications. Static gap; no claim of delayed real care.

### G03 — High — Consultation summary reads the wrong field names

- Requirements: 20, 31, 45, 46, 69. Evidence: E12 repository `getDoctorReviewProjection:948` returns raw Mongoose lean tasks/prescriptions/procedures/referrals/follow-ups; E17 component asserts snake_case shapes at `:25` and renders them. E15 API returns `Record<string, unknown>` without a summary parser.
- Expected: saved clinical/operational data renders accurately and safely in the summary presented for approval/print.
- Actual: task `testName` is read as `test_name`; prescription `items` are expected as `medications`; raw source identifiers/other camelCase fields are similarly assumed mapped. Clinical review and optical resources are mapped, so the mismatch is selective, not every field. Additionally, the component labels any present optical current record “Approved Optical Prescription” without checking optical status (`OphthalmologyConsultationSummaryCard.tsx`, optical section). `getConsultationSummary` (`ophthalmology.service.ts:1154`) reads the current projection rather than returning the frozen approved snapshot alongside its approval; approved-versus-current display semantics need explicit separation.
- Impact: omitted/blank test and treatment details can mislead summary review and print output.
- Recommendation: server-owned minimal typed summary DTO, runtime response schema, and realistic raw-model-to-UI contract/rendering tests.
- Dependencies: specialty repository/client/summary component; shared domain DTOs. Static finding.

### G04 — High — Field-level clinical completeness remains configuration-dependent and unproven

- Requirements: 14, 16, 17, 21, 23, 28, 67. Evidence: E09 `configured-result-fields.ts:5–44`; base posterior form at `result-fields.ts:31`; UI explicitly says a saved structured value may be preserved while its control is unavailable at `OphthalmologyTestsWorkspace.tsx:122`; E10 configured validators.

- Actual: 21 families exist, but nested fields are added only from configured numeric/choice/unit paths; unsupported structured values are not editable in generic controls. Original field-level FSD and approved deployed master values were not available. The generic Release 2 FSD does not supply these ophthalmic field contracts.
- Impact: presence of a family cannot establish clinically complete entry; required paths may block completion or lack adequate controls.
- Recommendation: restore field-level FSD, map each required field to UI/API/model and approved profile; add focused field tests. Never seed guessed clinical values.
- Dependencies: clinical owner, master configuration, form contracts and document policy. Mixed static limitation/acceptance gap.

### G05 — High — Shared registration/check-in retain non-atomic paths

- Requirements: 1, 4, 6, 64, 78. Evidence: E01 patient create writes patient then timeline separately; E03 createFromAppointment uses E23 `executeTransaction`, whose fallback reruns without a transaction on unsupported MongoDB.
