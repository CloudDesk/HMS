# Ophthalmology OPD Codebase and BA Assessment

Assessment date: 14 October 2026 (Asia/Calcutta). Scope: the currently checked-out HMS source, local requirements and targeted tests. Application code, configuration, databases, test fixtures and Git history were not changed. This report is the only authored deliverable.

## 1. Executive Summary

**The full Ophthalmology OPD requirement is not ready for feature implementation as an approved clinical contract.** The encounter, patient, authorization, service catalogue, laboratory, imaging, prescribing, dispensing, procedure, referral, follow-up and billing foundations are reusable. However, the current code does not implement the station-based, per-eye, reviewed and amendable clinical workflow described in `Ophthalmology_OPD_Understanding_Document.docx` (hereafter **UD**).

The UD is an interpretation of an underlying FSD marked **For Review and Approval**, not a complete approved field specification. Its sections 9, 12, 15 and 16 already establish many requirements: preserve OD/OS separately, axis 0–180, prevent silent post-completion overwrites, retain repeat lineage, separate optical from medication prescriptions, and restrict portal publication. Do not ask stakeholders whether these are desired again. Ask for the unresolved clinical values, policies and implementation contracts listed in section 13.

The most consequential code findings are:

- OPD laboratory/imaging submission requires a **completed consultation**. The UD requires tests and review while the encounter remains open. Changing this ordering affects General OPD, completion and billing.
- One clinical-order aggregate exists per visit and order type, with multiple service items but **one lifecycle status**. This is not a per-test assignment queue and cannot independently represent repeat, cancellation, performer, station or review of each item.
- Diagnosis selections are appended to consultation assessment text. There is no structured diagnosis identity, certainty, laterality, severity, primary/secondary designation or downstream diagnosis reference.
- No dedicated Dental clinical implementation was found in this checkout. Dental department fixtures and older Dental test log filenames are not evidence of a reusable Dental examination implementation. No Ophthalmology module, optical prescription, station/device master or specialized eye-test model was found either.
- Consultation finalization spans several writes without a transaction. Generic visit transitions lack an expected-status/version predicate. These are source-confirmed technical limitations; no live failure or patient harm was observed.
- Diagnostic result verification gates portal results. Uploaded patient documents follow a different path: active documents are listed/downloadable without a clinical-publication allow-list. This conflicts with automatically treating all attachments as approved portal material.
- Shared service prices and procedure prerequisites are configurable. Eye-test clinical ranges, eligibility, mandatory-test rules and reviewer assignment are not established configuration capabilities.

The immediate next work is approval and contract design plus remediation planning for the demonstrated shared-code risks. No implementation phase has started. Three selected mocked frontend suites passed, **15 tests total**; database integration, production behavior and full regression remain unverified.

## 3. Existing HMS Architecture Relevant to Ophthalmology

### Encounter and shared clinical ownership

`PatientModel` owns identity and demographics, with a patient number and registration branch. `OpdVisitModel` owns appointment linkage, patient, assigned doctor, doctor specialization, branch, department, visit type, priority and queue status. `OpdVisitService.createFromAppointment` and `createWalkInVisit` resolve existing patient/doctor/appointment records. Appointment-linked creation uses a transaction; the appointment index is unique. `ensureNoActiveVisit` checks active visits, but no active-patient unique index was found.

The same visit anchors consultation, vitals, prescriptions, clinical orders, referral and follow-up. `ClinicalSourceContext` also supports Emergency, inpatient and procedure contexts. This is the correct reuse boundary for specialty records. It is not evidence that a dynamic specialty form framework exists.

Visit transitions are defined by `allowedVisitStatusTransitions`: CHECKED_IN → WAITING_FOR_VITALS → READY_FOR_CONSULTATION → IN_CONSULTATION → COMPLETED, with skip/cancel/no-show branches. SKIPPED can return to IN_CONSULTATION; COMPLETED, CANCELLED and NO_SHOW have no outgoing transitions. `callNextPatient` uses a transaction and conditional claims. Generic `updateStatus` validates the previously read state but updates by ID and branch, not expected state/version.

### UI and integration structure

`OpdVisitPage` composes the current workspace through `useOpdVisitFeature` and `useOpdWorkspace`; domain hooks, service adapters and API clients provide the existing reusable approach. The page still contains diagnosis state and billing-service selection logic, so conformance to the desired layering is incomplete. Reuse patient headers, tabs, builders, `DiagnosticQueue`, `DiagnosticWorkspace`, document upload components and permission/error/loading patterns. Do not copy prototype state into these hooks.

`modules/index.ts` actually registers OPD, laboratory, imaging, surgery and other shared routes. No Dental/Ophthalmology registrar was found. `Scope/HMS Local/opd-module.js` and `imaging-module.js` contain richer prototype behaviors, including critical-result and attachment controls. These are interaction references, not proof of device, alert or clinical integration.

### Authorization and audit

`requirePermission` authenticates and resolves active database permission tuples, auditing denials. `PermissionRepository.userHasPermission` checks active user, active role and active permission; browser role names do not authorize API calls. Seed role grants distinguish reception, nurses, doctors, laboratory, imaging, pharmacy and billing. Seed configuration is not proof of deployed grants. Laboratory entry and verification have separate actions, but the default Laboratory User is granted both; separation of duties is not enforced merely by action naming.

`OpdVisitRepository.resolveBranchScope` enforces active assigned branches with a super-admin exception. Dashboard scope additionally considers departments/linked doctors; ordinary consultation access resolves branch scope only. No organization discriminator was established in the inspected patient/OPD models. An organization isolation guarantee cannot be inferred from branch checks or deployment assumptions.

Audit events record actors and event metadata through existing infrastructure, but event existence does not imply prior/new clinical values or immutable amendment versions. The distinction is material for the UD.

## 11. Security, Clinical Safety, and Data Integrity Review

### Verified controls and their limits

- API authentication and active database permission checks exist. Direct requests without a matching grant are rejected by middleware; this source conclusion is not a newly executed full authorization penetration test.
- Branch access is derived from active assigned branches. Organization isolation and assignment ownership need a separate explicit contract. Patient identity exists centrally; a registration branch is not evidence of exclusive patient ownership.
- Laboratory `EnterResult` and `VerifyResult`, and imaging equivalents, distinguish actions. They do not prohibit the same user performing both, and no per-test approval configuration was found.
- Diagnostic transition updates compare the old order status within transactions; result/report entry and verification are coordinated with audit. Unverified value edits have no request version, so no blanket lost-update guarantee is justified.
- Unique indexes prevent multiple aggregate results/orders for the same key, not repeat lineage or identical-request idempotency at all endpoints. Submitted OPD orders return existing content, whereas other context methods reject differing retries.
- Submitted prescription editing is blocked; pharmacy confirmation includes version/idempotency/stock safeguards. This does not provide a general clinical prescription amendment or optical revision system.
- Verified results are protected from ordinary edits, but UD requires authorized amendments that preserve previous values. Immutability without a correction path is only partial support.

### Required safety contracts

The shared diagnosis model must retain clinical certainty, laterality and stable references without converting technician observations or machine readings into diagnoses. Separately saved OD/OS records must survive copy-normal, reload, repeat and wrong-eye correction. OU must not silently replace required eye-specific values. Numeric validation must preserve UD's specified axis bounds while applying approved scales/units/ranges for other measurements.

Completion must validate approved mandatory tasks, reviewed/deferred results, abnormal acknowledgements, prescription/plan approval, follow-up decision and authorized digital approval on the server. Permissioned overrides must retain pending responsibilities and reasons. Core completion and downstream billing/order results need an explicit transaction or recoverable idempotent workflow with visible partial failure.

Publish by approved record/field/file status, not merely by being attached to a patient. Portal family access must continue through accessible-patient resolution, and final summaries must exclude internal doctor/test notes. A verified result flag must not implicitly approve unrelated uploaded images or documents.
